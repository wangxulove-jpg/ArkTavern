## Goal

Allow per-group-chat modification of character card fields (description, personality, scenario, etc.). These overrides ONLY affect AI prompt generation within that specific group chat — the global Character card in the app is never modified.

## Scope / Non-goals

**In scope:**
- Override `name`, `description`, `personality`, `scenario`, `systemPrompt`, `mesExample`, `postHistoryInstructions`, `firstMessage`
- Persist overrides in RDB per `(chat_id, character_id)` composite key
- Apply overrides during `GroupPromptAssembler.assemble()` for the speaking character
- UI entry point: `GroupMemberManagePage` — tap a member to open override editing sheet
- Per-member display name override also affects chat history and narration

**Out of scope:**
- Global character card modification (explicitly forbidden)
- Override for `avatarUri`, `characterBookId`, `tags`, `creator`, `extensions`
- Per-member override in single chat (single chat uses `Chat.userNameOverride` only)
- World scene chat overrides (world mode has separate instance system)

## Current State And Constraints

### Where character data flows for group chat generation

1. **ViewModel**: `GroupChatViewModel.loadMembers()` loads `Character.name`, `Character.avatarUri`, `Character.description` into `GroupMemberUiModel`
2. **RoundCoordinator**: `buildSpeakersForTarget()` loads Character just to check existence
3. **GroupPromptAssembler.assemble()** (line 214): Loads FULL `Character` via `characterService.getById(speakerCharacterId)` — this is the injection point
4. The Character object is passed to `PromptBuilder.build()` which calls `buildCharacterSystemContent()` to assemble the system prompt

### Existing override patterns
- `Character.userName`: per-character `{{user}}` override (in `characters` table)
- `Chat.userNameOverride`: per-chat `{{user}}` override (in `chats` table)
- Neither covers per-group-chat character field overrides

## Design

### Data Model: `GroupCharacterOverride`

```typescript
export interface GroupCharacterOverride {
  readonly id: string;               // UUID
  readonly groupConversationId: string; // chats.id (group mode)
  readonly characterId: string;         // characters.id
  readonly name: string | null;
  readonly description: string | null;
  readonly personality: string | null;
  readonly scenario: string | null;
  readonly systemPrompt: string | null;
  readonly mesExample: string | null;
  readonly postHistoryInstructions: string | null;
  readonly firstMessage: string | null;
  readonly createdAt: number;
  readonly updatedAt: number;
}
```

Only non-null fields override the original Character. If all fields are null, the override record is effectively unused (or can be deleted).

Create/Update uses upsert semantics: one override per `(groupConversationId, characterId)`.

### Database: v32 migration

New table:
```sql
CREATE TABLE IF NOT EXISTS group_character_overrides (
  id TEXT PRIMARY KEY NOT NULL,
  group_conversation_id TEXT NOT NULL,
  character_id TEXT NOT NULL,
  name TEXT,
  description TEXT,
  personality TEXT,
  scenario TEXT,
  system_prompt TEXT,
  mes_example TEXT,
  post_history_instructions TEXT,
  first_message TEXT,
  created_at INTEGER NOT NULL,
  updated_at INTEGER NOT NULL
)
```

Index: `UNIQUE (group_conversation_id, character_id)` to enforce one-override-per-member.

Cascade delete: when a group chat is deleted (via `ChatPersistenceOperations.removeChatWithMessages`), delete all overrides for that chat in the same transaction.

### Repository: `GroupCharacterOverrideRepository`

Pattern follows `GroupCharacterMemoryRepository`:
- `getByGroupAndCharacter(chatId, characterId)` → single override or null
- `upsert(override)` → insert or update (upsert by composite key)
- `deleteById(id)` / `deleteByGroupWithStore(store, chatId)` (for cascade)
- Row ↔ model conversion functions

### Service: `GroupCharacterOverrideService`

- Thin wrapper around repository
- Key method: `applyOverrides(character: Character, overrides: GroupCharacterOverride): Character`
  - Returns a new Character object with overridden fields where override value is non-null
  - `name` override changes both the speaker's displayed name AND the `{{char}}` macro
- `getOverrides(chatId, characterId)` → loads and caches (single fetch per speaker per round)

### Injection: `GroupPromptAssembler.assemble()`

At line 214, after loading the speaker character:
```typescript
const speaker: Character | null = await this.characterService.getById(context.speakerCharacterId);
// NEW: apply overrides
const overrides: GroupCharacterOverride | null = await this.overrideService.getOverrides(
  context.chatId, context.speakerCharacterId
);
const effectiveSpeaker: Character = overrides !== null
  ? this.overrideService.applyOverrides(speaker, overrides)
  : speaker;
```

The `effectiveSpeaker` replaces `speaker` throughout the rest of `assemble()` — including:
- `loadParticipantNames()` — if name is overridden, the participant name list reflects it
- `promptBuilder.build()` — receives overridden character
- `buildIdentityBoundary()` — uses overridden name
- `convertHistoryMessages()` — sender names reflect overrides

Also need to load overrides for participant names via `loadParticipantNames()`. Currently it only loads `.name` from Character. Should also check overrides for each participant to get the effective name.

## Risks And Compatibility

- **Migration safety**: v31→v32 adds one table and one index. No ALTER on existing tables. Rollback-safe.
- **Performance**: Override lookup is O(1) per speaker per round (PK lookup). No caching needed.
- **ArkTS strictness**: All `GroupCharacterOverride` fields are `readonly`. applyOverrides() creates a NEW Character object (immutable pattern).
- **Backward compat**: Group chats without overrides work exactly as before — `getOverrides()` returns null, no Character is modified.
- **SDK version**: No new API usage beyond existing `@kit.ArkData` (RDB) and `@kit.ArkUI` (Sheet).
